## 3. 冲突处理优先级

如文档之间出现冲突，按以下顺序处理：

1. 用户最新明确决定。
2. `design.md` 中的视觉和组件规范。
3. 产品需求文档中的业务范围与产品规则。
4. 模块专项文档中的详细业务规则。
5. Figma 总 Brief 中的生成说明。

发现冲突时不得自行选取更方便实现的一项。先修正真源文档，再同步其他文档。

## 4. 已确认的关键决策

| 主题 | 已确认决策 |
| --- | --- |
| 一级模块 | 人体、训练计划、饮食管理、个人 |
| 社区 | 首版移除，由饮食管理替换 |
| 目标用户 | 新手、减脂、增肌、家庭训练、功能性训练；未来可扩展 |
| 客户端 | React Native，同时支持 iOS 与 Android |
| 3D | Unity as a Library；男性与女性；精细解剖树；远程模型资源 |
| 3D 资源 | 基础低精度模型随安装包，高精度层通过对象存储和 Addressables 下载 |
| 肌肉粒度 | 可展示到肌肉分部、起止点、肌腱和韧带；只有有训练意义的节点可作为动作筛选目标 |
| 人体交互 | 选择肌肉后镜头推进并高亮，再进入动作筛选 |
| 后端 | Spring Boot |
| 数据库 | MySQL |
| 媒体 | 对象存储，建议配合 CDN |
| 管理后台 | Vue |
| 饮食数据 | FatSecret Platform API 中文区为主，服务端适配供应商字段 |
| 短信 | 阿里云短信，仅验证码、账号安全和重要通知 |
| 普通提醒 | App Push 与本地通知，不使用短信 |
| 商业体验 | 全程无广告 |
| 内容来源 | AI 可生成初稿，发布前必须人工专业审核 |
| 参考产品 | Workout.cool 只借鉴流程模式；不复制其品牌、资产、文案、代码、广告和付费结构 |

## 5. 文档维护规则

- 产品范围变化先更新 PRD，再更新模块专项和页面清单。
- 视觉 token 或组件行为变化先更新 `design.md`，再更新 Figma 组件。
- 数据字段或接口变化先更新数据与 API 文档，再修改代码。
- 每份文档顶部维护版本和日期。
- Figma 页面和开发任务应引用具体文档章节，避免只引用聊天记录。
